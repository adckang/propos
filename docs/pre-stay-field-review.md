## ACT-02 · 장치·센서 읽기 전용 조사

### 접근과 현재 워처

- 처음에는 기존 SSH 공유 연결이 종료돼 HA의 기존 접근 정보와 Pi의 GET API로 조사했다. 이후 사용자가 공유 SSH를 복구해 실제 프로세스·기동 설정까지 읽었다. 비밀번호·토큰·전체 구동 환경변수는 출력하지 않았다.
- Pi `GET /api/monitoring/state`: 파주201, `OCCUPIED / GOOD_CONDITION`, WebSocket 정상, 오류 없음, 준비 회차 없음, 이벤트 전송 대기 0건, 상태 저장 오류 없음.
- Pi `GET /api/properties`: `watcher1`, 지역 `파주`, 기존 장치 역할 9개 모두 `null`, `optimization` 없음. 22:20 KST SSH로 읽은 실제 워처 설정도 지역 `파주`, 제어 장치 역할·최적화 매핑 없음이었다. 메타데이터의 빈 역할 목록과 실제 워처 설정을 구분해 확인했다.
- HA `GET /api/states`와 `POST /api/template`의 순수 `areas()`·`area_entities()` 조회: 파주201 영역 41개 엔티티 확인. 서비스 호출·상태 변경 템플릿을 사용하지 않았다. 카메라 영상·출입 기록은 조회하지 않았다.
- Pi의 HA 접근과 이번 조회의 접근이 같은지는 일회성 해시를 메모리에서만 비교해 확인했다. HA 대상·인증값 모두 일치했으며 해시·비밀값 자체는 기록하지 않았다.

첫 조회 시각: **2026-11-07 22:00:23 KST**. 제조사·모델은 HA의 `device_attr` 읽기 전용 조회에서 모두 `Tuya / T & H Sensor`로 확인했다. 이 모델 표기만으로 정확한 무선 방식·제조사 보고 주기 설정 방법을 확정하지 않는다.

### 제어 장치와 적용 제약

- 파주201 영역에 등록된 `climate`·`humidifier`·`fan`·`water_heater` 엔티티는 이번 조회에서 없었다. 조명·콘센트·스위치를 냉난방 장치로 임의 지정하지 않았다.
- HA 전체의 `climate.byeoggeolihyeong_eeokeon`은 **다른 영역** 소속이며 지원 모드는 `off / cool / dry / fan_only`다. `heat` 모드가 없으므로 난방에 사용할 수 없고, 물리적으로 파주201의 장치인지도 확인되지 않았다. 이 장치를 자동으로 가져오거나 영역을 바꾸지 않았다.
- 실제 사용하는 방에 ‘안방창고’가 포함되는지, 방별 냉난방·가습·제습 설비가 무엇인지 사용자 확인이 필요하다. 엔티티 이름만 보고 침실과 장치 관계를 확정하지 않는다.
- 센서 보고 주기 검증, 사용할 방·실제 제어 장치 연결이 해결되기 전에는 ACT-07의 실행 가능한 매핑을 확정할 수 없다. 신선도 기준을 완화하거나 오래된 측정 시각을 현재 시각으로 바꿔 통과시키지 않는다.

### 2026-11-08 사용자 확인 · 공간과 적외선 제어

**확정 사실:** 파주201은 방 3개짜리 숙소이며 공간은 손님이 사용한다. ‘안방 창고’는 베란다 성격이라 다른 실내 공간과 온습도 차이가 크고 이불·침구를 보관한다. 직접 제어 가능한 HVAC 대신 적외선 기기로 에어컨을 켜고 끌 수 있고, 같은 공간의 온습도계로 온도 변화를 관찰할 수 있다고 사용자가 설명했다. 침구 보관 공간을 없는 공간으로 제외하거나 일반 침실과 같다고 가정하지 않는다.

**HA 읽기 전용 대조:** `scene.eeokeonon_off` / ‘에어컨on/off’를 찾았지만 영역 미지정 상태다. `remote.send_command` 서비스는 없고 `scene.turn_on`은 등록돼 있다. 해당 씬이 파주201의 실제 IR 경로인지, 단일 전원 반전 명령인지 켜기·끄기 분리 명령인지는 질문 응답 대기다. `scene.hwangi_on/off` 등도 있지만 이를 에어컨 명령으로 대신 연결하지 않는다.

씬의 실제 GET 상태는 `unknown`이었다. 이는 물리적인 에어컨의 켜짐·꺼짐을 뜻하지 않으며, 이름만 보고 고장이나 전원 토글 방식으로 확정하지 않는다. 씬을 실행해 보지 않았다. 다른 영역의 `climate` 장치도 임의로 가져오지 않았다.

현재 실제 순수 함수에 **가상 입력**으로 신선한 고온·정상 습도 센서와 IR 씬을 주어 호환성을 검사했다. `cool_device_unavailable_or_unsupported` 등 오류와 명령 0개를 반환했다. 이는 현재 코드가 IR을 직접 지원하지 않는다는 근거이며 실제 파주201에 가상 데이터를 저장하거나 제어한 시험이 아니다.

**미구현 검토안:** 안방 창고의 침구 보관 상태는 거주 공간과 역할을 구분해 명세하되, 전체 준비의 필수 조건인지·습도 중심 보관 기준을 어떻게 둘지는 구체적인 사례와 기준을 먼저 비교한다. IR 지원 역시 단순 엔티티 매핑으로 끝낼 수 없고, 명령·피드백·정지 계약과 회귀 테스트를 제시한 뒤 별도 코드 수정 승인 범위로 진행해야 한다. 현재 목표·상태 판정·보고서 계산·제어 코드는 변경하지 않았다.

### 2026-11-09 추가 조사 · IR 장면의 제공 범위와 센서 보고

**이번에 완료한 범위:** HA 레지스트리·장치별 진단·센서 상태의 읽기 전용 조사와 설치 버전의 공식 소스 대조다. ACT-02 전체 완료나 실제 제어 연결 완료를 뜻하지 않는다. 장면 실행, HA 설정 변경·재시작, Pi 재시작, 운영 인증 POST, 실제 알림·업무 이벤트 전송은 하지 않았다. SSH 공유 연결이 종료됐지만 이번 조회에는 필요하지 않아 재접속을 요구하지 않았다.

#### IR 장면과 실제 장치를 구분한 결과

15:34~15:39 KST, HA WebSocket으로 영역·엔티티·장치·통합 레지스트리와 `diagnostics/get`을 조회했다. Tuya 통합은 `loaded`이며 장치별 진단을 제공했다. **`scene.eeokeonon_off`의 연결 장치는 모델 `Tuya Scene`, 유형 `service`인 장면용 등록 객체다.** 물리적 IR 송신기와 연결됐다는 증거가 아니며 엔티티·장치의 HA 영역도 모두 미지정이다.

## ACT-03 · 날씨·알림 경로

### 날씨

- Pi 저장 메타데이터와 SSH로 읽은 실제 워처 설정의 지역은 모두 `파주`다. 과거 지역명이 비어 있던 기록을 현재 값으로 재사용하지 않는다.
- HA에서 `weather.forecast_jib`은 ‘Forecast 집’으로 위치 미확정, `weather.sujigu_sinbongdong`은 다른 지역인 수지구이며 관측도 오래됐다. `weather.jib`은 `unavailable`이었다. 자동으로 어느 것을 파주 날씨로 지정하지 않았다.
- 기존 `fetchWeather('파주', null)` 공통 함수의 실제 조회: 지오코딩 결과 `KR / 경기도 / 파주`, Open-Meteo 응답 성공. 조회 22:06:04 KST, 자료 시각 22:00 KST, 온도 1.4°C·습도 65%. 정확한 숙소 좌표나 주소는 외부로 보내지 않았다. 기상청 키가 없는 대체 경로를 검사한 것이며 Pi의 기상청 키 유효성을 확인한 결과는 아니다.
- 첫 로컬 Node 시도에서는 `UNABLE_TO_VERIFY_LEAF_SIGNATURE`가 발생했다. 인증서 검증을 끄지 않고 해당 진단 프로세스에서만 시스템 CA 사용 옵션을 켜 재조회에 성공했다. 앱·Pi·OS의 인증서나 환경변수를 변경하지 않았으며 이 로컬 진단 오류를 Pi/운영 날씨 장애로 단정하지 않는다.
- 적용 후보는 **기존 파주 지역 조회 경로 재사용**이다. 다른 지역 HA 날씨는 제외한다. 정확한 숙소 좌표가 필요하면 검증된 값만 별도로 확인하며, 실물 주소를 추정해 저장하지 않는다. 위 기온을 기존 순수 목표 함수에 적용할 경우 초기 정책의 21°C·허용 20~22°C·습도 35~50% 구간이다. 현재 숙소 환경을 제어한 결과가 아니다.

**Pi 자체 조회의 추가 재현:** 22:24~22:29 KST, 실제 워처 설정을 사용한 별도 프로세스에서 기존 어댑터는 처음 `null`, 하위 `fetchWeather`는 502·`지오코딩 실패: fetch failed`였다. 외부 DNS는 조회됐으나 Node에서는 IPv4 연결 `ETIMEDOUT`·IPv6 `ENETUNREACH`가 묶여 실패했다. 같은 Pi의 curl은 200, 프록시 변수는 없었다. 운영 공통 `/api/weather?district=파주`도 Pi에서 200·기상청 자료를 반환했다.

Node의 주소별 연결 대기는 기본 250ms였다. 별도 진단 프로세스에서 IPv4만 사용하면 지오코딩 200이었다. IPv4 고정 대신 `--network-family-autoselection-attempt-timeout=1000`만 적용한 별도 프로세스에서도 **기존 `getPreparationWeather`가 Open-Meteo 온습도와 원본 자료 시각을 반환**했다. 앱 계산을 바꾸거나 OS의 IPv6를 끄지 않았다. 따라서 최소 후보는 Pi Node 기동 인자에서 연결 대기를 1,000ms로 늘리는 것이다. 이 비교는 현재 환경의 재현·개선 근거이며 모든 네트워크 장애가 영구히 사라진다는 보장은 아니다. 이후 사용자 승인으로 같은 기동 인자를 실제 워처에 반영했다. 아래 ACT-06 반영 결과와 검증 한계를 함께 따른다.
